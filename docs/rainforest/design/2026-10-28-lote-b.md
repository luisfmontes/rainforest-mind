# Lote B: paralelo por tarefa, esperar-ci, Issue de outro repo, teto proporcional e catraca (#613, #610, #616, #614, #612, #606, #609)

## Objetivo
Tirar seis defeitos do próprio fluxo, todos vistos em uso real entre 26 e 28/10: o despacho
paralelo fora de repo cai em série (#613, #610), o `esperar-ci` dá vermelho antes de o run
existir (#616), o `gate-fechar-issue` consulta a Issue no repo errado (#614), o teto de despachos
trava plano grande por construção (#612), e a catraca de mutação repete baseline (#606) e não
sobe monorepo com `raiz:` (#609). Versão 2.0.6 (PATCH: só conserto).

## Decisões fechadas
- **D1 — Alvo e convivência: serve ao Luís e a quem usa o plugin (Jefferson, repos busquei e ultron) nos estágios `executar`, `verificar` e `fechar`; cada conserto substitui o comportamento atual, sem chave para o antigo** — porquê: os seis comportamentos atuais só produzem trava falsa ou consulta errada; não há o que preservar.
- **D2 — #613/#610, branch de tarefa: `resolver` e `diagnosticar` (`hooks/lib/estagio-ativo.cjs`) aceitam, além de `fluxo/<slug>`, a forma `fluxo/<slug>-t<n>` (regex `-t\d+$`, só dígitos). Casamento exato vem primeiro: a forma `-t<n>` só é tentada quando nenhum fluxo aberto casa com a branch inteira. A mensagem de diagnóstico da portaria passa a dizer `espera fluxo/<slug> ou fluxo/<slug>-t<n>`. A skill `executar` documenta que, fora de repo (#565, worktree criado à mão e declarado na linha `Worktree:`), cada tarefa paralela ganha um worktree em `fluxo/<slug>-t<n>` criado da ponta de `fluxo/<slug>`** — porquê: a portaria lê a branch do despachante dentro de repo (`raizDoProjeto` usa `payload.cwd`), e ali o paralelo já funciona; o caminho quebrado é o fora de repo, em que a portaria lê a branch do worktree declarado (`worktreeForaDeRepo`), e o git não deixa a mesma branch em dois worktrees. Sufixo livre (`fluxo/<slug>-<qualquer>`) ou barra (`fluxo/<slug>/t1`) foram descartados: ver abaixo. Os quatro chamadores do `resolver` (portaria, `gate-teto-despachos`, `gate-agente-em-voo`, `limpar-worktrees`) passam a ver o worktree `-t<n>` como do fluxo; para `limpar-worktrees` isso protege o worktree de tarefa de ser removido enquanto o fluxo está aberto, que é o desejado.
- **D3 — #616, run ainda não registrado: quando os workflows do checkout alcançam PR (`workflowsDePr` > 0 ou desconhecido), o `esperar-ci` sonda `gh pr checks <pr> --json name,bucket` antes do `--watch` até a lista vir não vazia, a cada 10 s, com teto de 300 s (`RFM_CI_PRAZO_REGISTRO_S` sobrescreve, no molde de `RFM_MERGE_PRAZO_S`). Lista não vazia → segue para o `--watch` de hoje. Teto estourado → o caminho de hoje (exit 5 com "no checks reported"). Repo sem CI de PR (exit 8) não muda** — porquê: o GitHub leva minutos para registrar o run de um PR recém-criado (PR #615: o run apareceu minutos depois), e o 5 imediato mandava `reabrir` por um vermelho que não existe.
- **D4 — #614, Issue de outro repo: `extrairIssuesCitadas` devolve `{numero, repo}` e reconhece três formas depois da palavra-chave: `#N` (repo `null`, vale o repo do comando), `owner/repo#N` e `https://github.com/owner/repo/issues/N` (repo da citação). `verificarIssuesCitadas` consulta cada Issue no repo dela, e a mensagem de bloqueio nomeia `owner/repo#N` quando o repo veio da citação. Modelo de ameaça: protege contra a sessão ou o agente fechar, por engano, uma Issue sem comentário de evidência, inclusive Issue de outro repo citada por URL ou `owner/repo#N`. Fica fora: `GH_REPO` exportado em linha anterior ou no ambiente (o gate já barra a atribuição de prefixo na linha do `gh pr merge`), alias de shell, fechamento pelo site, e desligar o gate de propósito (`RAINFOREST_GATE_OFF`/config)** — porquê: hoje a URL de `repoB` é consultada em `repoA`, e um marcador em `repoA#12` libera o fechamento de `repoB#12` sem evidência. O modelo escrito é o critério de parada da revisão.
- **D5 — #612, teto proporcional: o teto padrão passa a ser `max(40, ceil(1,5 × tarefas))`, em que `tarefas` conta os cabeçalhos `### <n>. ` do plano. O cálculo mora em `hooks/lib/teto-despachos.cjs`, que o gate e a `cobertura` já compartilham, e o contador de tarefas é um só: a lib exporta o contador, e `estado.cjs` passa a usá-lo (ou uma bateria prova os dois iguais no mesmo texto). `teto-despachos:` declarado continua vencendo. A `cobertura` (`conferir-fluxo.cjs`) avisa quando o teto declarado é menor que o número de tarefas. A negação diz que a conta é cumulativa por fluxo e mostra `tarefas do plano: N`** — porquê: com padrão fixo de 40, um plano de 43 tarefas trava por construção, não por laço (fluxo `app-qbens-subprojeto-a`, 27/10). Contador duplicado sem teste é a divergência que o próprio `estagio-ativo.cjs` documenta.
- **D6 — #606, baseline uma vez: `conferir-fluxo.cjs mutacoes` mede o baseline uma vez por chave `(bateria, raiz, timeout)` e repassa o resultado às tarefas seguintes pela flag nova `--baseline-de <arquivo.json>` do `conferir-mutacao.cjs`. A primeira tarefa de cada chave grava o baseline com `--baseline-para <arquivo.json>`. O arquivo guarda `status` (sempre 0: só baseline verde é gravado), `duracao`, `stdout` e `stderr`, que alimentam a detecção de corte e de colapso. Vale só no modo cópia: `no-lugar: sim` mede o baseline a cada tarefa, porque o fonte real é reconferido entre tarefas** — porquê: no PR #605, seis tarefas apontavam para a mesma bateria de cerca de 7 min, e 5 dos 18 passes da bateria eram baseline repetido. A opção B (`filtro:`) fica fora de escopo.
- **D7 — #609, cópia do toplevel: com `--raiz` dentro de um repositório git, `copiarRaiz` copia o toplevel inteiro (sem o `.git` de topo, como hoje) e a bateria roda em `<cópia>/<caminho da raiz relativo ao toplevel>`. `--arquivo` continua relativo a `--raiz`. Com `--raiz` fora de git, vale o comportamento atual. `materializarGit` opera sobre o toplevel copiado** — porquê: em monorepo, o app importa uma pasta irmã (`../../Backend/...`, repo busquei, 26/10) e a cópia só da pasta do app não sobe. O contorno `no-lugar: sim` traz o risco que a cópia existe para evitar (#266).
- **D8 — Entrega: um PR, versão 2.0.6 em `.claude-plugin/plugin.json`, com README e CHANGELOG no mesmo PR; o corpo leva `Closes` de #613, #610, #616, #614, #612, #606 e #609, cada uma com comentário de evidência** — porquê: a trava `conferir-versao` exige bump para mudança executável, e o README acompanha toda entrega. D6 e D7 tocam os mesmos dois arquivos (`conferir-mutacao.cjs`, `conferir-fluxo.cjs`) e vão em série.

## Avaliado e descartado
- **#613 com branch `fluxo/<slug>/t<n>`**: o git não aceita a ref `fluxo/<slug>/t1` enquanto existe `fluxo/<slug>` (conflito arquivo/diretório em `refs/heads`), e a branch do fluxo existe durante todo o fluxo.
- **#613 com sufixo livre (`fluxo/<slug>-<qualquer>`)**: é ambíguo com slugs que são prefixo um do outro, e esse caso existe no repo (`gate-worktree` e `gate-worktree-552`/`-brechas`/`-home`, `zerar-issues` e `zerar-issues-10` a `-15`, todos em `docs/rainforest/estado/`). Nenhum slug existente termina em `-t\d+`.
- **#613 com o `preparar-worktree.cjs` trocando a branch do agente para `-t<n>`**: dentro de repo, a portaria lê a branch do despachante, não a do worktree do agente (`raizDoProjeto` usa `payload.cwd`), então trocar a branch do agente não muda a admissão. O caso quebrado é o worktree criado à mão fora de repo, e ali quem cria a branch é a sessão.
- **#606 rodando as tarefas da catraca em paralelo**: foi a carga da máquina que estourou o timeout da primeira tentativa no PR #605.
